# DXXRebirth hybrid core for MiSTer (Descent and Descent II)

## This core

- Name everywhere: `DXXRebirth` (the engine: core, folders `games/dnk/DXXRebirth/` and `logs/dnk/DXXRebirth/`, `_Other/dnk/dnk-DXXRebirth_*.rbf`, release), `dxxrebirth` (game submodule, log, lock). The user asked for "DXX-Rebirth"; `new_core.sh` takes no hyphen. The games and their menu entries (`_Other/dnk-<title>.mgl`): `package/games.txt`, `d1|Descent` and `d2|Descent II` (set names `DXXRebirth_d1`, `DXXRebirth_d2`; logos `package/logos/d1.png`, `d2.png`), in the zip as `games/dnk/DXXRebirth/games.txt`, from which the database's build makes the launcher's catalogue.
- The game is `dxxrebirth/`, branch `mister` (upstream dxx-rebirth master). Its MiSTer code is behind the SCons option `mister_hybrid=1` (`DXX_USE_MISTER_HYBRID`), most of it in `common/arch/mister/` (`mister_port.cpp`, `mister_music.cpp`). The fork is `ItsDanik/dxx-rebirth` (remote `origin`, default branch `mister`; `upstream` is dxx-rebirth's), the core `ItsDanik/DXXRebirth_MiSTer` (public since 2026-10-23).
- Build: `./build.sh` (game), `./core/build_core.sh` (FPGA), `./package.sh` (zip in `dist/`), `MISTER=root@<address> tools/deploy.sh`.
- Release: the zip in `releases/`. Players get it once it is published to the database, only when Danik asks: `hybrid/launcher/distribution.py publish ~/dnk_Distribution_MiSTer releases/DXXRebirth_YYYYMMDD.zip` (the rule in `hybrid/CLAUDE.md`).
- Try a build on the MiSTer without installing it: `MISTER=root@<address> tools/test_on_mister.sh d1|d2|list|nodata|log|stop` (the rule in `hybrid/CLAUDE.md`). It mirrors the data of the old folders (`games/d1x-rebirth`, `d2x-rebirth`) when the new one has none.
- Lines marked `GAME:` in the scripts and `TODO` in the READMEs are the places the template left for this game.

## Only this game

- Two games, three binaries: `DXXRebirth` (`src/dxxrebirth.c`) is what the launcher starts; it picks the game with `MH_PickGame()` (the menu entry's set name, or the list when the core was loaded by itself; `d2demo` is the shareware of `d2`), closes the library with the logo still up (host version 17) and execs `d1x-rebirth` or `d2x-rebirth` with `-hogdir` the data folder. The data of both games is in one folder, `games/dnk/DXXRebirth/` (DATADIR, USB first); what the games write is in `descent/` and `descent2/` there (`D1X_REBIRTH_HOME`, `D2X_REBIRTH_HOME`), missions in their `missions/`. The games look for their data in `descent/` and `descent2/` first (as upstream in `~/.d1x-rebirth`), so the chooser accepts each game's files there too (`find_at_home()`; Danik's own data was there, 2026-10-23). The launcher moves the first versions' `games/d1x-rebirth` and `games/d2x-rebirth` there.
- The build is SCons, not CMake, and needs gcc 14 and Python 3.10: `toolchain/Dockerfile` (image `mister-dxxrebirth-tc`) has a gcc 14.3 cross compiler built against the glibc 2.31 of the hybrid toolchain. `tools/deps.sh` builds PhysFS, SDL2_image and libADLMIDI (patched, see the music below; the image has no `patch`: `git apply`).
- The ARM build has `-fno-tree-vectorize`: gcc 14.3 miscompiles a NEON shift in `check_vec` (vecmat.cpp), which breaks the level geometry. Keep it unless a newer compiler is verified.
- Upstream only has the software renderer for SDL 1.2; `similar/arch/sdl/gr.cpp` has our SDL2 path. Upstream master is not tested with the software renderer or the shareware data: several fixes in the fork are for that, not for the MiSTer.
- The game's clock is the core's field counter (`MiSTer_RunTime` in `timer_update`). The game has wait loops on that clock, so `MiSTer_RunTime` also checks that the core is alive and leaves with `_Exit` if not.
- Speed: the Cortex-A9 has no divide instruction. `c_tmap_scanline_per_span` (scanline.cpp, the default here, `-tmap c` is upstream's) divides once per 16 pixels instead of twice per pixel, and `fixdiv` uses the FPU with an exact correction on ARM. Before adding a division to anything that runs per pixel, per vertex or per object, think of that.
- Profiling for ARM without a MiSTer: a `-pg` build (`lto=0`) run under `qemu-arm` with a script that quits through the menus (gmon.out is not written on `_Exit`), then `arm-linux-gnueabihf-gprof`. qemu's time follows the instruction count, software division included, so it shows what x86 profiles hide. First user report on hardware: 30-40 fps before the span mapper.
- Loading the core again while a game runs: `MH_CoreReloaded()` and exit code 43, which `danik_hybrid_launch.sh` answers by starting `DXXRebirth` again.
- Descent II movies: frames are drawn (and the 640x480 ones scaled) by `MovieShowFrame` in movie.cpp, not by `gr_bm_ubitbltm`, which calls two functions per pixel. The movie sound must wrap at 16 bits (`processSwath`, mve_audio.cpp). The retail data to test with is in `~/.d2x-rebirth` on the user's PC (high resolution movies only); never copy it into the repository.
- Measuring on the MiSTer (see the memory note for its address): `MISTER_HYBRID_STATS=1` in the environment makes the game log, every 600 frames, how many fields each frame took and how long it worked, every late frame with what it waited for, and (from `hybrid/hps`) how full the audio ring stayed. `hybrid/tools/fbmon.c` shows from outside whether every field got a new frame. A `-pg -DDXX_MISTER_PROFILE` build (`build/armpg.sh` in the build folder is the recipe) run by hand with `/tmp/dxxrebirth_nolaunch` set writes `gmon.out` when the core is unloaded. Measured on 2026-10-05: a frame of Descent level 1 takes about 5 ms, a menu frame took 10 ms before the menu fixes.
- Things that stalled frames and must stay cheap: sounds are converted when first played (`-sdlmixer-resampler=`; the default here is `emulate-sdl1`, SDL's own converter took 50-100 ms per sound), the menus load the palette every frame (`gr_palette_load`, `gr_remap_color_fonts`), and a frame of the game waits for its field at its start (`MiSTer_WaitFrame`), not when it is shown.
- Frame pacing: `DRAW_AHEAD` in `mister_port.cpp` is 0 (each frame shown as soon as it is made). Not benchmarked yet on host version 17: run a level with `MISTER_HYBRID_STATS=1` and `MISTER_HYBRID_PACE=1`, with `DRAW_AHEAD` 1 and with `MISTER_HYBRID_AHEAD=0`, and write the numbers and the decision here (`hybrid/CLAUDE.md`, "Frame pacing"). A level frame took 5 ms on 2026-10-05, so 0 is expected to stay.
- Testing without a MiSTer: `./build.sh host` with `hybrid/tools/fakecore`, and the ARM binaries under `qemu-arm` in the toolchain image (`QEMU_LD_PREFIX=/opt/mister-sysroot`). The shareware data of both games is free (icculus.org/d2x/data); `build/data/` has them unpacked. A fresh home asks for a pilot (Enter takes the default), then New Game asks for the level and the difficulty, then the briefing (Esc).
- dnkLauncher screenshots, `package/screens/<id>.png` (2026-10-26): 320x200 as fakecore's `shot` saves it, `MISTER_HYBRID_FPS=0`, the retail data, a fresh pilot whose highest level was raised in `player.plr` (the `LevelNum` of its mission's entry: D1 the one without a name, D2 `d2`) so New Game starts the level without a cheat; the briefing skipped with Esc, then flying in with the keyboard and firing the lasers, Rookie, the default cockpit (D1) and full-screen HUD (D2) of a new pilot. d1 level 6, Mercury Solar Lab (lasers at the robots of the first tunnel), d2 level 3, Wenl Mine (lasers down a corridor).

## 240 lines and the HUD margins

- *Resolution* (status bit 24) is 320x200 or 320x240. `grd_curscreen` is always 320x200 (`Game_screen_mode`, `SWIDTH`/`SHEIGHT`): in 320x240 the window and its surface are 320x240 and the screen's canvas is the 320x200 in the middle, so menus, briefings, titles, movies, the automap and the letterbox view stay as they are, centred. `gr_flip` blacks the 20 rows above and below in a frame where the game did not draw its view (`MiSTer_GameFrameDrawn()`). A change in the OSD calls `gr_set_mode` from `MiSTer_CheckCore` (not during a movie) and the cockpit is set up again at the next frame.
- In the game (`init_cockpit`, `game_render_frame_mono`): `Screen_3d_window` is the whole 320x240 frame (`MiSTer_FrameCanvas()`) in the full screen, status bar, cockpit and rear view modes; `MiSTer_cockpit_layout` keeps where the view is in the 320x200 layout. Each frame the cockpit picture, the status bar, the gauges and Descent II's inset views are drawn to a 320x200 canvas whose bottom is at the bottom margin (the view goes on below it: no black strip, `hybrid/CLAUDE.md`), and the HUD to a canvas from the top margin down to where the view ends in that layout; the reticle, the mouse indicator and the names over objects stay on the view's canvas (`MiSTer_view_canvas` in `draw_hud`). The view's pixels are square in 240 lines (`sc_aspect` from the window: 1.0), so it shows what the 320x200 one shows, with the same field of view.
- The texture mapper stopped at `SWIDTH*SHEIGHT` pixels (a guard against writing past the screen), which cut the view at row 200: it is the frame's size now (`MiSTer_frame_pixels`). Sub-canvases take the font of their parent: `MiSTer_FrameCanvas()` copies the screen's, or the HUD has none (a crash).
- Menu mask: bit 0 while in 320x200 (greys *HUD (Top)* / *HUD (Bottom)*), bit 1 in Descent (greys the cheats only Descent II has). `HUD_EDGES` is 2'b11.

## Gamepad

- Defaults since 2026-10-23 (Danik): left stick and d-pad turn and pitch, right stick slides, R2 / L2 fire primary / secondary, Y / X flare / bomb, B / A accelerate / reverse, L / R cycle primary / secondary, Select rear view, Start the menu; Slide On has no button. `J1` (core) and `DefaultKeySettings` (kconfig.cpp) must agree. The triggers are bound as the axis buttons of axes 4 and 5 (`DXX_MISTER_AXIS_BUTTON`: joystick 1's 32 buttons and its hat come first), pressed past 30%. The d-pad pushes the left stick (axes 0 / 1) all the way, except in a direction the left stick is pushed in: Main_MiSTer presses the d-pad too when the left stick is pushed far (as in CrispyDoom), which made a half-tilted stick turn at full speed (and, with the sticks swapped, turned the ship while the left stick slid). For the same reason a d-pad press Main_MiSTer made from the left stick is not the d-pad's for the controls, in play or when binding (`joy_mister_dpad_from_stick()`; menus still move with the stick through it), and a d-pad direction the player bound to a control or weapon only does that and no longer pushes the stick (`kc_mister_bind_dpad()`): an Xbox One controller's player bound the d-pad and found the left stick firing those bindings and the d-pad still turning the ship (2026-10-24; checked with fakecore, not yet on the MiSTer). Two test builds that day had the right stick turning and the left sliding, the first of them with the triggers as an analog throttle (one axis of both, R2 forward): Danik preferred firing on the triggers and turning with the left stick. A pilot whose joystick bindings are still the first defaults, or a test build's, gets the current ones when it is read (`kc_mister_update_joystick`); one the player changed is left alone.

## Music, cheats, rumble

- The music is libADLMIDI's sequencer and HMI instrument banks, as on a PC, but played by the core (`mister_music.cpp`): `tools/libadlmidi-mister.patch` adds an emulator `ADLMIDI_EMU_HOOK_OPL2` (one OPL2, 9 voices) whose register writes go to a hook with the frame they are at, and the raw MIDI events hook. With the OSD's *Music* on MIDI (`MH_MidiWanted()`) the song's events go to the synthesizer or an MT32-pi (GM reset and the song's settings sent again on a switch, a new song or `MH_MidiSynthChanged()`, the song held while `MH_MidiBacklog()` goes out), else the OPL2 writes go to the core's FM chip (loaded again from a register shadow on a switch back). Without the core's chip (or the patched library) the software OPL3 plays it as upstream. FM volume 64 (twice the chip's own, as upstream mixes the software chip twice as loud): not yet compared by ear on the MiSTer.
- Cheats (OSD page 2): the options and triggers run the typed cheats' code (`do_cheat` in gamecntl.cpp, from `MiSTer_GameFrame` after each frame), one player only and not in a demo, and zero the score as typing does. Invulnerability is put back on a new ship. *Next Level* starts the next level of the mission directly, as the level warp does (not from a secret level, not after the last).
- Rumble (status bit 25, on by default): jolts that fade (`MiSTer_Rumble` in `mister_port.cpp`, as CrispyDoom's), sent every frame from `MiSTer_CheckCore`. Hits (`apply_damage_to_player`), shots by weight (`do_laser_firing_player`, `do_missile_firing`), walls (`collide_player_and_wall`, force fields), the ship's death, and every frame while the reactor countdown, a seismic tremor or the fusion charge go on (`mister_rumble` in gamecntl.cpp).
